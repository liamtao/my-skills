# A2B2 多线程开发与设计验收

协调聊天默认直接担任“开发需求总管”，维护整批进度。也可显式委派给项目角色 `DevelopmentManager`。同一批保留一个协调者。每个 feature 聊天独占自己的工作目录，交付可复现的版本。用中文向 Ben 汇报可看的页面、要判断的行为和待决定的交付范围。

## 从修改需求启动

Ben 提出实现或迭代需求后，协调者主动安排工作。先用验收清单和 Git 对照每项需求，然后按下表执行。Ben 已要求修改时，无需他额外说“开 worktree”或再次批准常规本地开发。

| 收到的需求 | 当场执行 |
| --- | --- |
| 同时实施多个 feature，或在已有批次中追加独立 feature | 按可单独验收的行为拆分，逐项寻找合适的已有 worktree。缺少时通过当前客户端的 worktree 创建入口建立主题分支及工作目录，核实实际路径、分支和基线，再登记并启动该项代码修改。 |
| 修改已经在做或验收中的 feature | 找回原负责人、分支和 worktree。已暂停则恢复；正在展示旧版则先结束该项预览。把反馈交回原目录实施，完成后交付新的 SHA。 |
| 两项需求改动同一行为，或后一项依赖前一项 | 同一行为交给一个负责人统一修改；能分别验收的真实依赖项按下文的分支技能建子层。只有产品意图有冲突时才向 Ben 确认范围。 |
| 仅讨论方案、询问状态或查看某个预览 | 读取当前登记和证据，按所问范围展示。待收到实现请求后再建开发 worktree。 |

单一小改动若已有合适的主题分支及干净、无其他负责人占用的工作目录，直接复用。确实需要独立并行写入时，给每项分配独立 worktree；只有已确认的依赖才从父分支分出。

## 用 Team Mode 开发与初审

1. 读取 `ben-a2b2-team-mode`，由它管理角色、模型、首次派工准备及并发限制。协调者记录每项负责人的目标、独占的绝对工作目录、实际分支、预期行为和验收场景，通过 Executor 启动或接续实现。已有 feature 聊天在推进时复用该负责人，避免重复派工。
2. 拿到稳定提交后，将同一 base、head SHA、验收要求和证据交给独立 Reviewer，按 `a2b2-code-review` 做初审。发现影响验收的问题就退回原负责人修订，再审新 SHA。缺少真实设备或测试条件时，记录未验证项。
3. 如果总管作为子 agent 运行且无法继续派工，把每项任务的角色、目录、范围、版本和验收要求交回主聊天，由主聊天按 Team Mode 派发并收回结果。若派工能力不可用，说明实际执行方式和独立初审缺口，初审状态以真实结果为准。

## 开工与恢复

- 开始或恢复时，按[本机并行设计验收手册](/Users/ben/.config/a2b2/dev-tools/README.md#并行设计验收)执行 `dev review list`。用实际 Git 分支和 HEAD、监听进程与 GitHub PR 校准登记信息。以手册中的工具维护验收卡，复用现有记录。
- 每项记录用户可见的结果、目标端、负责人或聊天、worktree、依赖和目标场景。复用已有聊天；Ben 明确要求时才新建用户可见聊天。同一文件可按行为分工，同一行为指定一位负责人。共享能力先明确验收范围与依赖。
- 独立 feature 从刷新后的 `origin/main` 分出；有真实依赖时引用 `a2b2-stacked-branches` 记录父分支和边界。按本机手册登记 worktree 和预览。运行环境引用 `ben-a2b2-start-dev`，涉及额外服务或资源隔离时再引用 `a2b2-parallel-env`。
- 技能按名称读取目标 checkout 的当前项目入口。若 worktree 缺少被 Git 忽略的个人技能链接，去主 checkout 的 `.agents/skills/` 或 Skills Manager 读取，实际操作仍指向已登记的 worktree。

## 交付一轮设计验收

1. Feature 聊天自检、提交，交付干净的 SHA 并暂停编辑。验收卡显示 feature、端、短 SHA、直达链接或模拟器场景、应看到的变化及截图；动效附短录屏。区分待看、已通过和受阻的端。
2. 协调聊天按点名打开固定端口的 Portal 页面，或在专用验收 worktree 将同一台验收模拟器切到指定提交。端口与构建操作沿用本机手册。浏览器逐端口核对账号、角色、首次使用状态、视口和测试数据，使页面可比。跨端交互按 `a2b2-mobile-ux` 交付，实机或浏览器场景验证引用 `a2b2-local-e2e`。
3. Ben 确认后按 **feature × 端 × SHA** 登记通过。收到回改，把反馈交给原负责人，重新交付新 SHA 并复核受影响的端；其他 feature 可继续。
4. 已通过的 feature 共用页面、导航、组件或状态时，用专用验收目录从明确基线和成员 SHA 生成组合，只复走交集场景。把回归交给来源分支修复；基线或成员变化后重建并复核。无交集的已通过项可先交付。

初审完成后，在协调聊天一次列出本轮待 Ben 验收的功能，每项一行。入口必须对应本轮实际运行的提交。Portal 提供可点击的目标页；iOS 提供设备、页面和必要操作。先验证入口能展示该功能，登录或首次使用会影响显示时写出最短前置步骤。尚未就绪的项单列原因，修完一项可先交该项。Ben 确认前保留“待设计验收”状态。

| 功能与端 | 已初审 SHA | Review 入口 | 操作与预期 | 证据及验证缺口 |
| --- | --- | --- | --- | --- |
| 本轮可验收的行为 | 短 SHA | 目标 URL 或设备与页面 | Ben 应操作什么、看到什么 | 截图或录屏，以及待验证项 |

## 验收前确定交付范围，通过后自动交付

同批多个独立 feature 就绪且尚未指定交付方式时，列出候选项及依赖，**主动问 Ben 这批分别提 PR，还是合成一个 PR**。复用该批已明确的选择。存在未落地祖先时由 `a2b2-stacked-branches` 确定可选范围。在展示最终验收清单前确定交付单元、目标端和 base。由下游技能提前取得本批 Sprint 选择，已有选择直接沿用，让 Ben 在同一轮看到交付范围和完整工单草稿。

- **分别提交**时，各项独立推进。某项的目标端全部通过后，在各自 worktree 以该 feature 的实际 diff 和证据调用 `ben-a2b2-submit-pr`。
- **合并提交**时，按本机手册建立独立交付分支，只纳入已选提交。等待该交付单元全部目标端通过及交集验收完成后提交。核对实际 base 到 head 的完整 diff；在该分支验证组合结果，每项分别附验收证据，再调用同一 PR 入口。在每张来源卡记录源 SHA、交付 SHA 和同一个 PR 链接。
- 验收卡注明将自动提交的 PR 范围及关联的具体工单草稿，最终确认同时批准该交付单元及所示草稿。单端阶段确认只推进该端进度。Ben 确认最终通过后，立即调用 `ben-a2b2-submit-pr` 跑门禁、提交 PR，并把已确认的工单批次交给下游按实际 PR 校准、写入和读回。附上 PR 与工单链接，并保留实际落地提交待核验。已明确的“只看设计”“仅 PR”“先给我看草稿”等本次指令优先。

## 生命周期

- **暂停与恢复**：暂停时释放该项运行资源，登记恢复点并保留分支。恢复时核对原卡、worktree、HEAD、监听归属和 PR，按实际版本重新开启预览。
- **合并与整理**：协调聊天在用户同步 main 后、恢复批次或接收下一批需求时，核对未结项 PR。已合入远端 main 时刷新远端引用；需要更新本地 main 时只在持有 main 的干净工作目录安全快进。本地 main 或远端证据有分歧则保留并报告。按本机手册核对每个来源 SHA、交付 SHA、落地提交及 worktree 的额外工作。处理需保留的文件与占用后，调用 `a2b2-stacked-branches` 的整理流程，在已证实范围迁移子分支、验证并自动删除已完整落地的本地分支。合并 PR 使用 cherry-pick 或 squash 时逐项核对，证据不足的来源分支保留。记录已归档、已删除和仍待处理的项。
- **取消**：登记取消原因并释放本流程启动的服务。涉及删除未合并工作、关闭 PR 或改写已发布历史时，以 Ben 对具体动作的授权为准。
