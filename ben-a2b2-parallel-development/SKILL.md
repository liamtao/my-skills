# A2B2 分支开发与设计验收

协调聊天默认担任“开发需求总管”，也可显式委派给项目角色 `DevelopmentManager`。同一批保留一个协调者。每个工作目录同一时间只交给一位负责人写入。用中文汇报验收入口、预期行为和待决定的交付范围。

## 从修改需求启动

先用 Git 核对当前分支、HEAD、未提交文件和目录占用，再按需求依赖选分支起点，按是否需要同时保留两份工作现场选目录。

| 收到的需求 | 当场执行 |
| --- | --- |
| 顺序实施新需求 | 默认复用当前 checkout。确认目录干净且可切换后，延续当前版本的需求按 `a2b2-stacked-branches` 建子分支，独立需求从刷新后的 `origin/main` 分出。多项需求可依次实施时依次用同一目录。 |
| 当前改动还在推进，同时启动另一项 | 原任务留在原目录。有并行写入、需保留在跑的预览，或 Ben 明确要求隔离时，优先复用合适的已有 worktree，缺少时通过客户端的 worktree 入口为新任务创建。核实实际路径、分支和起点后开工。是否已有 PR 只影响交付安排。 |
| 接着上一轮已交付的版本开发 | 派工前按「接续已交付版本」核实来源 PR、实际起点和下一轮 PR base。 |
| 回改已经在做或验收中的 feature | 找回原负责人和分支，复用该分支当前检出的目录。已暂停则恢复。正在展示旧版时先结束本流程为该项启动的预览，再交付新 SHA。 |
| 两项需求改动同一行为 | 由同一负责人在对应分支内实现。明确需要单独交付的依赖项才建子层。 |
| 仅讨论方案、询问状态或查看预览 | 读取现有记录和证据，按所问范围展示。 |

并行新分支同样按依赖选择起点。独立插单从最新 `origin/main` 起步。依赖插单从父分支已提交且包含所需改动的 SHA 起步，并按 `a2b2-stacked-branches` 记录父分支和边界。所需改动仍未提交时，保留父目录现场，先做只依赖已提交内容的准备工作，等父层有可用提交再启动依赖实现。

## 用 Team Mode 开发与初审

1. 读取 `ben-a2b2-team-mode`，由它管理角色、模型、首次派工准备及并发限制。协调者记录每项负责人的目标、绝对工作目录、实际分支、预期行为和验收场景，通过 Executor 启动或接续实现。已有 feature 聊天在推进时复用该负责人。
2. 拿到稳定提交后，将同一 base、head SHA、验收要求和证据交给独立 Reviewer，按 `a2b2-code-review` 做初审。发现影响验收的问题就退回原负责人修订，再审新 SHA。缺少真实设备或测试条件时，记录未验证项。
3. 如果总管作为子 agent 运行且无法继续派工，把每项任务的角色、目录、范围、版本和验收要求交回主聊天，由主聊天按 Team Mode 派发并收回结果。若派工能力不可用，说明实际执行方式和独立初审缺口，初审状态以真实结果为准。

## 开工与恢复

- 每项记录用户可见的结果、目标端、负责人或聊天、分支、工作目录、起点 SHA、依赖和目标场景。复用已有聊天。Ben 明确要求时才新建用户可见聊天。
- 串行项及主 checkout 上的任务在协调聊天记录验收与 PR 信息，复用该目录的开发和验收环境。附加 worktree 按[本机并行设计验收手册](/Users/ben/.config/a2b2/dev-tools/README.md#并行设计验收)用 `dev review list` 查找旧卡，并用实际分支、HEAD、进程与 PR 校准登记。需要启动环境时用 `ben-a2b2-start-dev`，有额外服务或资源隔离再用 `a2b2-parallel-env`。
- 读取目标 checkout 的技能入口。缺少个人技能链接时，从主 checkout 的 `.agents/skills/` 或 Skills Manager 读取。Git 和验收操作仍在已核实的目标目录执行。

### 接续已交付版本

1. 从验收记录找出包含所选功能的交付 PR，从 GitHub 读回状态、base、交付分支、PR head 和落地 SHA。资料缺失或 PR head 变化时，用已验收 SHA 和交付 diff 核实要继承的改动。已有并行验收卡时，可用[本机手册](/Users/ben/.config/a2b2/dev-tools/README.md#pr-与退出)的 `dev review continuation` 核对远端提交。
2. 开放 PR 的回改沿用交付分支和原 PR。需要独立交付且依赖开放 PR 时，从核实的 PR head 建子分支，记录父分支和边界，子 PR base 指向交付分支。PR 已合入 `main` 时，从包含落地 SHA 的最新 `origin/main` 开始，PR base 为 `main`。已有子分支时，按 `a2b2-stacked-branches` 迁移子层并核对 diff。
3. 按「从修改需求启动」选择工作目录。核对分支、HEAD 和未提交文件后，报告来源 PR、起点 SHA 和本轮 PR base。PR 关闭未合入、合入其他分支或来源证据不明时，先核实起点。

## 交付一轮设计验收

1. 实现负责人自检并交付干净的 SHA，待验期间暂停该版本的编辑。验收记录列出功能、端、短 SHA、直达链接或模拟器场景、预期变化和截图，动效附短录屏。标明各端是否就绪。
2. 单个版本在其 checkout 的环境中核对 SHA 和入口。Portal 并排验收时，复用主 checkout 已核对的入口，对已登记的附加 worktree 使用本机手册的固定端口。逐端口核对账号、角色、首次使用状态、视口和测试数据。需要切换并行 iOS 版本时按本机手册使用专用验收目录。跨端交互按 `a2b2-mobile-ux` 交付，浏览器或模拟器验证引用 `a2b2-local-e2e`。
3. Ben 确认后按 **feature × 端 × SHA** 登记通过。收到回改，把反馈交给原负责人，重新交付新 SHA 并复核受影响的端；其他 feature 可继续。
4. 多项改动有交集时，依赖项可直接在已包含父层的子分支 SHA 上复核组合行为。需组合验证不同分支时，用专用验收目录从明确基线和成员 SHA 生成组合，只复走交集场景。成员均已登记时可用 `dev review integrate`。把回归交给来源分支修复，基线或成员变化后复核。无交集的已通过项可先交付。

初审完成后，在协调聊天一次列出本轮待 Ben 验收的功能，每项一行。入口必须对应本轮实际运行的提交。Portal 提供可点击的目标页；iOS 提供设备、页面和必要操作。先验证入口能展示该功能，登录或首次使用会影响显示时写出最短前置步骤。尚未就绪的项单列原因，修完一项可先交该项。Ben 确认前保留“待设计验收”状态。

| 功能与端 | 已初审 SHA | Review 入口 | 操作与预期 | 证据及验证缺口 |
| --- | --- | --- | --- | --- |
| 本轮可验收的行为 | 短 SHA | 目标 URL 或设备与页面 | Ben 应操作什么、看到什么 | 截图或录屏，以及待验证项 |

## 验收前确定交付范围，通过后自动交付

默认每个 feature 分支提交自己的 PR，包括从独立 worktree 开发的分支。Ben 明确要求合并交付时，按本机手册为选中的功能准备组合。展示最终验收清单前，写明每个 PR 的范围、目标端和 base，由下游技能处理 Sprint 选择和工单草稿。

- **独立需求**以 `main` 为 PR base，在其分支实际检出的目录用该功能的 diff 和证据调用 `ben-a2b2-submit-pr`，可独立评审和合入。
- **依赖需求**从底到顶逐层提交。父层未落地且已有 PR 时，子层以父分支为 base 提 draft PR，评审子层自己的改动。父层尚未提 PR 且未到交付条件时，可继续准备子层，等父 PR 建立或落地再提子 PR。父层已落地时，按团队规则迁移子层并使用 `main`。沿用同一范围已明确的逐层策略，由 `ben-a2b2-submit-pr` 和团队门禁核对实际 base、授权和 draft 条件。已获授权连接原生 GitHub stack 时，走该技能的链式提交入口。
- **合并提交**只纳入 Ben 点名的提交。各项目标端全部通过后，在交付分支核对完整 diff、验证组合并附各项证据，再调用同一 PR 入口。保留原验收 SHA，并关联同一个交付 PR。
- PR 创建或更新后读回 GitHub，记录实际 base、交付分支、PR head 和链接。确认落地 SHA 包含在刷新后的 `origin/main` 后，补记落地证据。
- 验收记录注明将自动提交的 PR 范围及关联的具体工单草稿，最终确认同时批准该交付单元及所示草稿。单端阶段确认只推进该端进度。Ben 确认最终通过后，立即调用 `ben-a2b2-submit-pr` 跑门禁、提交 PR，并把已确认的工单批次交给下游按实际 PR 校准、写入和读回。附上 PR 与工单链接，并保留实际落地提交待核验。已明确的“只看设计”“仅 PR”“先给我看草稿”等本次指令优先。

## 生命周期

- **暂停与恢复**时，释放本流程为该项启动的运行资源，登记恢复点并保留分支。恢复时核对该分支当前目录、HEAD、监听归属和 PR，按实际版本恢复预览。
- **接回主栈**通过各 PR 合入 `main` 并同步其后的分支完成。独立 PR 落地后，刷新 `origin/main`，在主栈可安全更新时按 `a2b2-stacked-branches` 吸收新基线。依赖 PR 按父层先落地、子层再对准 `main` 的顺序推进。先核对 GitHub 已更新的 base 和 head，再按同一技能处理仍需迁移的提交，核对每层 diff 并复查受影响的验收场景。PR 合并及已发布历史改写遵守各自授权。
- **整理**时，核对来源和交付 SHA、落地证据及目录中的额外工作，按 `a2b2-stacked-branches` 清理已完整落地的分支和符合条件的附加 worktree。活跃或有未提交文件的目录留待下次安全同步。记录已处理和待处理的项。
- **取消**：登记取消原因并释放本流程启动的服务。涉及删除未合并工作、关闭 PR 或改写已发布历史时，以 Ben 对具体动作的授权为准。
