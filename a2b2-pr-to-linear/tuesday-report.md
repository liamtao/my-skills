# Dot 给 Ashok 的周二周报

沿用 Ben 已有的邮件模板、语言和语气。以此次周报对应的周二为基准，使用 Asia/Singapore。回顾段取上周三开始、到本周二收尾的 Sprint，计划段取次日周三开始的 Sprint。重跑同一期时仍用原来的周二。按团队和起始日期核对 Linear Cycle ID，以 issue 实际所属 Cycle 归入对应段。

## 1. 先固定本期清单

- 通过 ben@a2b2.ai 确认 Ben 的 Linear 身份。分页读完收尾 Sprint 中当前指派给 Ben 的 issue，保存 ID、原状态和原 assignee。这是本次可提议更新的范围。下个 Sprint 的票仅用于写计划。
- 周报还应包含这两个 Sprint 内有 PR 或交接记录证明由 Ben 交付、随后转给别人的工作。按 Cycle 查找并核对贡献证据，用 issue ID 去重。保留本期清单至邮件生成，转派后仍按原 ID 读回。多人协作时写清 Ben 的部分。

## 2. 核对状态并一次确认

逐票解析验收负责人。优先使用 issue 明确指定的人，其次取正文 Stakeholders 区块中按原始顺序列出的第一人，区块为空或缺失时取 Linear 的 issue creator。用 Linear 用户身份匹配 Ben。若人名无法唯一解析，保留原值并注明原因。

逐票检查实现该项交付所需的 PR。在 GitHub 中把实际合入的提交与对应应用成功的 SIT 发布记录核对，记录发布链接及版本。使用覆盖该改动的有效版本，考虑 squash merge、回滚和多 PR 交付。iOS 等有独立构建或分发记录的端，核对对应 SIT 构建。能确定尚未部署才记为“否”。缺 PR、发布历史不可读、部分端或部分 PR 已部署且交付不完整，均列为待核实。

| --- | --- | --- | --- |
| Ben | 是 | Closed after Testing | Ben |
| Ben | 否 | Ready for Testing | Ben |
| 其他人 | 是 | Ready for Testing | 验收负责人 |

第一行按 Ben 的约定直接关单，SIT 发布凭据即满足本次状态条件。只有实际验收记录才能支持邮件中“已人工测试通过”的表述。保留已完成、取消、重复和归档记录。对待核实项保留现状。父项、子项分别按其自身归属及交付证据判断，关联关系不触发级联写入。

向 Ben 一次展示拟变更的 issue ID、状态和 assignee 的前后值、验收人的来源及 SIT 依据，另列待核实项。Ben 明确确认具体清单后才写入；没有差异时直接生成草稿。执行前复核 Cycle、状态、assignee、验收人和发布依据，跳过已有相同结果的项，对发生冲突的项单独说明。只提交批准的字段，逐票读回结果，按实际保存状态写周报。

## 3. 用原模板生成邮件草稿

- 回顾段按用户可见成果归并相关 issue，写清已交付、待部署、已交接验收或仍在推进，保留对应 Linear 和 PR 链接。计划段按次日开始的 Sprint 写具体下一步，已开发的功能可写部署或验收。没有明确下期归属的待办留作待确认。
- 凡本期邮件提到显著 UI/UX 变化，在对应成果旁放入同一场景的 **Before** 和 **After**，配一句用户能观察到的变化。优先从 Linear 读取原图，缺图时从关联 PR 补取；同一场景只展示一次。全新界面没有可比基线时，展示 After 并注明原因。
- 将图片作为邮件内嵌图片，或在邮件工具仅支持附件时附原图并在对应段落标出文件名。保留 PR 和 issue 的持久链接。预览草稿，核对每一对图片的内容、顺序和显示效果；若无法取图或验证显示，把具体缺口报告给 Ben。私有资源保留原访问权限。
- 将邮件草稿交给 Ben 审阅。对 Linear 批次的确认仅覆盖该批次；发送邮件另按 Ben 的明确指示执行。
