# A2B2 多线程开发与设计验收

协调聊天维护整批进度。每个 feature 聊天独占自己的工作目录，交付可复现的版本。用中文向 Ben 汇报可看的页面、要判断的行为和待决定的交付范围。

## 从修改需求启动

Ben 提出实现或迭代需求后，协调者主动安排工作。先用验收清单和 Git 对照每项需求，然后按下表执行。Ben 已要求修改时，无需他额外说“开 worktree”或再次批准常规本地开发。

| 收到的需求 | 当场执行 |
| --- | --- |
| 同时实施多个 feature，或在已有批次中追加独立 feature | 按可单独验收的行为拆分，逐项寻找合适的已有 worktree。缺少时通过当前客户端的 worktree 创建入口建立主题分支及工作目录，核实实际路径、分支和基线，再登记并启动该项代码修改。 |
| 修改已经在做或验收中的 feature | 找回原负责人、分支和 worktree。已暂停则恢复；正在展示旧版则先结束该项预览。把反馈交回原目录实施，完成后交付新的 SHA。 |
| 两项需求改动同一行为，或后一项依赖前一项 | 同一行为交给一个负责人统一修改；能分别验收的真实依赖项按下文的分支技能建子层。只有产品意图有冲突时才向 Ben 确认范围。 |
| 仅讨论方案、询问状态或查看某个预览 | 读取当前登记和证据，按所问范围展示。待收到实现请求后再建开发 worktree。 |

给每项负责人目标、独占写入目录、预期行为和验收场景，启动或接续实现并跟进至可验收提交。已有 feature 聊天优先接续；如当前环境允许委派，可在协调聊天内派发独立实现。没有独立执行者时，由当前聊天逐目录完成已授权修改并说明实际并发情况。

## 开工与恢复

- 开始或恢复时，按[本机并行设计验收手册](/Users/ben/.config/a2b2/dev-tools/README.md#并行设计验收)执行 `dev review list`。用实际 Git 分支和 HEAD、监听进程与 GitHub PR 校准登记信息。以手册中的工具维护验收卡，复用现有记录。
- 每项记录用户可见的结果、目标端、负责人或聊天、worktree、依赖和目标场景。复用已有聊天；Ben 明确要求时才新建用户可见聊天。同一文件可按行为分工，同一行为指定一位负责人。共享能力先明确验收范围与依赖。
- 独立 feature 从刷新后的 `origin/main` 分出；有真实依赖时引用 `a2b2-stacked-branches` 记录父分支和边界。按本机手册登记 worktree 和预览。运行环境引用 `ben-a2b2-start-dev`，涉及额外服务或资源隔离时再引用 `a2b2-parallel-env`。
- 技能按名称读取目标 checkout 的当前项目入口。若 worktree 缺少被 Git 忽略的个人技能链接，去主 checkout 的 `.agents/skills/` 或 Skills Manager 读取，实际操作仍指向已登记的 worktree。

## 交付一轮设计验收

1. Feature 聊天自检、提交，交付干净的 SHA 并暂停编辑。验收卡显示 feature、端、短 SHA、直达链接或模拟器场景、应看到的变化及截图；动效附短录屏。区分待看、已通过和受阻的端。
2. 协调聊天按点名打开固定端口的 Portal 页面，或在专用验收 worktree 将同一台验收模拟器切到指定提交。端口与构建操作沿用本机手册。浏览器逐端口核对账号、角色、首次使用状态、视口和测试数据，使页面可比。跨端交互按 `a2b2-mobile-ux` 交付，实机或浏览器场景验证引用 `a2b2-local-e2e`。
3. Ben 确认后按 **feature × 端 × SHA** 登记通过。收到回改，把反馈交给原负责人，重新交付新 SHA 并复核受影响的端；其他 feature 可继续。需要独立代码审查时引用 `a2b2-code-review`。
4. 已通过的 feature 共用页面、导航、组件或状态时，用专用验收目录从明确基线和成员 SHA 生成组合，只复走交集场景。把回归交给来源分支修复；基线或成员变化后重建并复核。无交集的已通过项可先交付。

## 选定 PR 范围

同批多个独立 feature 就绪且尚未指定交付方式时，列出候选项及依赖，**主动问 Ben 这批分别提 PR，还是合成一个 PR**。复用该批已明确的选择。存在未落地祖先时由 `a2b2-stacked-branches` 确定可选范围。设计通过后，等本批有提交 PR 的授权再推送。

- **分别提交**时，在各自 worktree 以该 feature 的实际 diff 和证据调用 `ben-a2b2-submit-pr`。
- **合并提交**时，按本机手册建立独立交付分支，只纳入已选提交。核对实际 base 到 head 的完整 diff；在该分支验证组合结果，每项分别附验收证据，再调用同一 PR 入口。在每张来源卡记录源 SHA、交付 SHA 和同一个 PR 链接。
- 把已确认的范围、检查、验收证据和 Linear 选择传给 PR 入口。由该入口调用团队门禁与建票技能，接续其具体草稿确认。按每项分别记录设计通过、PR 状态及实际落地提交。

## 生命周期

- **暂停与恢复**：暂停时释放该项运行资源，登记恢复点并保留分支。恢复时核对原卡、worktree、HEAD、监听归属和 PR，按实际版本重新开启预览。
- **合并后**：核实远端合并证据与落地 diff，检查来源分支有无额外提交、未提交或忽略的个人文件，以及仍依赖它的子分支。父 PR 被 squash merge 后交给 `a2b2-stacked-branches` 迁移子层，复查其 diff 和验收影响。核对完成后再登记完成、释放服务并归档对应 worktree。
- **取消**：登记取消原因并释放本流程启动的服务。涉及删除未合并工作、关闭 PR 或改写已发布历史时，以 Ben 对具体动作的授权为准。
