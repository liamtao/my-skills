# 量化框架版本升级

## 这个 skill 解决什么问题

官方框架不走 git 远程更新，而是每次发布一个带版本号的压缩包。本地仓库用两条分支承接：
`main` 保持官方原版（每次升级就是一次全量替换 + 一个提交），`dev`（或 `dev-v3` 等）
放自己的修改，通过 `git merge main` 把官方更新吸收进来。

难点不在 git 操作，而在**冲突解决时如何不丢东西**：官方跨大版本时可能重写核心链路，
而本地又有大量定制（真实数据路径、API key、自定义因子、格式化过的全仓代码）。
两边都改了同一个文件时，简单选一边都是错的。

## 开始之前

先跑侦察，把全貌拿到手再动任何东西。下列 `<技能目录>` 均指本次实际加载的
`SKILL.md` 所在目录，不要硬编码 `~/.Codex` 或其他安装位置：

```bash
python3 "<技能目录>/scripts/scout.py"
```

它会告诉你：官方分支与本地分支叫什么、当前版本 → 目标版本、官方包在哪
（含其他候选版本和新鲜度）、本仓库 main 的提交约定、以及**升级会新增/删除哪些文件**、
被 gitignore 的运行时数据有什么变化、工作区是否干净。

`--package PATH` 可手动指定包；`--hours N` 调整新鲜度窗口；`--json` 输出结构化结果。

读完输出后，先确认三件事，不对就停下来问用户：

- **本地分支识别对不对**。`local_branch` 为空或有多个候选时**必须问**——
  有的仓库把 `dev` 留作分叉备份，真正在用的是 `dev-v3`；合错分支后果很重。
- **官方包是不是想升的那个版本**。用户已明确指定包时使用 `--package`，不因新鲜度或其他候选重复确认；
  未指定时，有"窗口外"或无法判断目标的候选提示再核对。
- **工作区必须干净**。有未提交改动就先停下来，让用户决定提交还是暂存。

## 需要停下来问用户的三种情况

其余环节一路做完再汇报；以下处理选择若用户已经明确授权，按该选择执行，不重复询问：

1. **`only_in_main` 里出现非基建文件。** 全量替换会删掉它们，而若本地分支从未改动过，
   合并时会连带从本地分支一起消失。备份 tag 可恢复代码，但不能替用户决定日常使用的插件要不要保留。

   问之前先做一次判定，很多情况能自己定掉、不必打扰用户：
   **拿与当前官方分支版本一致的旧官方包比一比**，再查 `git log -- <文件>` 的来源。
   scout 的分类只是提示：`--package` 模式不会自动搜索旧包，自动模式的其他候选也不保证是当前旧版本。

   ```bash
   diff <(cd <旧版官方包> && find . -type f | sed 's|^\./||' | sort) \
        <(git ls-tree -r <官方分支> --name-only | sort)
   ```

   - 旧包没有且 git 历史明确为本地添加 → **保留**，不用问；仅一个旧包没有不能断言“从来不是官方的”。
   - 旧包或官方发布历史确认曾分发、新版没有 → 确认 main/dev 各自如何处理。可建议 main 跟随官方删除、
     dev 从升级前 tag 恢复兼容插件；若无明确来源，先说明未知。用户已给出处理选择时直接执行。

   `.gitignore` 这类明显的本地基建直接保留。反过来，如果官方包**自带** `.gitignore`，
   那就让官方版本落地 —— 本地对它的定制会在合并到本地分支时以冲突形式浮现，
   在那一侧解决才是对的位置。
2. **被 gitignore 的运行时数据要不要更新。** 例如 `data/` 下的最小下单量表、币种分类表。
   它们不进 git，`git diff` 看不见，但直接影响能否跑起来（官方改过 CSV 编码、加过新 json），
   而且可能是用户手工维护过的。要问，并且更新前先备份。
3. **官方跨了大版本且本地改动很重。** 从更新说明判断本次是否有架构级重写
   （例如 pandas → polars）。是的话先告诉用户"冲突会很多、部分定制需要改写而非移植"，
   确认继续再动手。

## 升级流程

### 1. 建立退路

```bash
git tag pre-<新版本>-<本地分支>-<唯一后缀> <本地分支>
git tag pre-<新版本>-<官方分支>-<唯一后缀> <官方分支>
```

记录两个 tag 的提交号，不用 `-f` 覆盖已有退路。tag 只能恢复已跟踪内容；不能恢复被忽略的运行时数据。
回退前还要检查是否出现升级后的新工作，不要用 `reset --hard` 抹掉它。运行时文件靠单独备份恢复。

### 2. 全量替换官方分支

```bash
git checkout <官方分支>
python3 "<技能目录>/scripts/apply_official.py" \
    --package <官方包路径> --preserve .gitignore <其他已确认保留文件...> --dry-run
```

脚本做四件事：删掉旧的已跟踪文件（`--preserve` 的除外）、写入官方代码、只清理由本次删除导致的空目录、
**精确暂存**。`--preserve` 接收逐个文件路径，不能只写目录名。先核对 `--dry-run`，再去掉该参数实跑。

要一起更新运行时数据就加 `--runtime-data copy --backup-dir <备份目录>`。脚本会在修改仓库前备份旧数据，
缺少备份目录直接拒绝；目录必须在仓库和官方包之外，且为新目录或空目录，不能覆盖旧备份。

暂存策略是这里的关键：官方分支的 `.gitignore` 往往极简，不覆盖 `__pycache__`/`.venv`，
所以**绝不能用 `git add -A`**，否则会把本地分支残留的 pyc 和虚拟环境提交进去。
脚本用 `git add -u` + 按官方清单显式 add，并在结束时自查暂存区有没有混入垃圾。

提交前用 `git diff --cached --stat` 核对，然后**照抄本仓库 main 的既有提交格式**
（scout 已经列出最近几条），不要自创格式。

### 3. 合并回本地分支

```bash
git checkout <本地分支>
git merge --no-commit --no-ff <官方分支>
```

先量一下冲突规模，决定怎么分工：

```bash
git -c core.quotePath=false diff --name-only --diff-filter=U
git diff --name-only --diff-filter=U -z | xargs -0 grep -c '^<<<<<<<'
```

同时看清双方的改动体量 —— 这决定每个文件该"以官方为骨架移植定制"还是"在本地基础上打补丁"：

```bash
git diff --stat <merge-base> <官方分支> -- <冲突文件...>   # 官方这次改了多少
git diff --stat <merge-base> <本地分支> -- <冲突文件...>   # 本地改了多少
```

`config.py` 单独提一句：它按行 diff 几乎必然是"本地改得多"，但那不代表可以整块留本地 ——
官方新增的键会跟着一起消失。合完之后一定要跑一次键级对账（验证步骤第 4 项）。

**注意 diff 行数会骗人**：官方只改 40 行、本地改了 300 行，不代表以本地为主 ——
官方那 40 行可能正是新架构的接入点，丢了整条链路就断。要判断的是官方改的是骨架还是叶子。

### 4. 派 subagent 解冲突

先按规模决定要不要派。实测下来，**5 个左右的冲突文件自己顺序解决反而更快**
（一次沙箱对比里，派 3 个 agent 解 5 个文件比自己解慢一倍、贵 20%，结果质量相同）——
派发、写简报、汇总报告的协调开销吃掉了并发收益。

值得并发的门槛大致是：**冲突文件 6 个以上，且分属 3 个以上互不相干的子系统**。
那时一般 3-5 个 agent，同一条消息里并发派发。规模不到就自己做，
但**判断原则照旧**（下面的简报内容依然是你自己解冲突时的标准）。

分组按**关注点**，而不是按文件数量平均分 —— 同一子系统的文件放一起，
agent 才能看到完整上下文（例如"资金曲线 + 评价指标 + 绘图"应当归一个 agent）。
最重、改动最大的文件单独给一个 agent。

顺带一提：本地分支的定制如果集中在 `factors/`、`signals/`、`sections/`、`positions/`
这类插件目录，而没碰过 `core/`，冲突往往少得出奇。先用 `git diff --name-only <merge-base> <本地分支>`
看清定制落在哪里，能避免为一个小合并摆开大阵仗。

先按 `references/merge-brief.md` 的模板生成简报写进临时文件，让每个 subagent
**先读简报再动手**。简报是跨 agent 的共同标准，保证大家用同一套原则判断，
不会各自发明规则合出自相矛盾的结果。

每个 subagent 的 prompt 里要给到：简报路径、它负责的文件清单、
该文件双方的改动体量、以及这些文件特有的注意事项（例如"官方在此重写了 1000 行，
以官方为骨架"或"本地曾在此修过 bug，检查官方新增内容是否需要同步扩展修复"）。

**必须明确禁止 subagent 动 git 索引**（`git add`/`commit`/`checkout`/`merge --abort`）——
并发时任何一个 agent 碰索引都会破坏其他 agent 的工作。主控统一暂存提交。

### 5. 验证

subagent 的报告不能直接采信，自己独立验证：

```bash
python3 "<技能目录>/scripts/verify.py" --since <升级前本地tag> --python <实际运行时解释器路径>
```

五层检查：残留冲突标记 → 全仓语法 → 占位符回归（只扫本次改动的文件）→
**config 键全集对账**（官方 config.py 有、本地没有的键）→
真实 import（递归扫描 core 与 configlib/factors/signals 等自定义目录，含新增 capital_flows）。
语法、配置 AST 与 import 均使用同一实际运行时解释器；默认优先 `.venv`，其他运行环境显式用 `--python`。
占位符增量范围包含已提交、已暂存、未暂存和未忽略新增文件，合并提交前也不能漏扫。
官方模块级配置键缺失默认验证失败；未找到静态读取点或 fallback 恰好同值都不能证明其他执行路径安全。

第 4 层可以脱离升级流程单独跑，用来体检往届欠账：
`python3 verify.py --no-import`（`--official-ref` 可指定官方分支，默认探测 main/master）。

还要**手工补三项脚本查不到的**：

- **跨文件依赖**。subagent 各管一摊，容易出现 A 文件 import 了 B 文件里已被删掉的符号。
  重点查各 agent 报告里互相提到的符号是否真的存在。
- **官方新特性是否真的落地**。从更新说明里挑出本次的重点新功能，
  grep 确认对应代码确实在合并结果里，而不是被本地版本盖掉了。

- **config 开关把执行路径导去了哪一侧**。这是最隐蔽的一类回归：代码全都在、
  语法全都对、import 全都通、连冲突标记都没有，但一个开关就让整条链路换了实现。
  两个方向都会出事，别只防一头：

  - **键在，导向官方新实现** → 你的旧实现定制变成永不执行的死代码。
    实例：官方新增 `report_version` 默认 `'v2'` 走新版报告，
    而本地在旧版报告文件里改了 500 多行，升级后一次都不会被调用。
  - **键不在，fallback 导向旧实现** → 撞上官方遗留在旧路径里的缺陷。
    实例：官方 `use_intraday_cache = True` 走有护栏的新因子链路，
    本地 config.py 缺这个键，fallback 成 `False` 走回旧链路，
    而官方在旧链路上漏了一处列过滤，于是个股择时回测直接 KeyError 崩掉。

  **必须是全集对账，不是"本次新增了哪些键"。** 上面那个 `use_intraday_cache`
  是官方 v2.3.0 就有的键，本地那次没接住，此后 5 次升级都只比对当次 delta，
  于是它永远进不了视野 —— 潜伏到某天真的走进那条分支才炸。
  `verify.py` 的第 4 步做的就是全集差集，别用"这次官方改了啥"替代它。

  **`config.py` 是全仓最容易漏键的文件**，因为解冲突时它几乎总该"以本地为主"
  （本地数据路径、策略清单、机器人 key 都在里面）—— 而整块取本地正是官方新键
  静默蒸发的机制，且不留任何冲突标记。所以它不能只靠第 3 步那种"按 diff 体量判断
  骨架还是叶子"，必须额外做一次键级对账。

  **特别当心 `hasattr` 判定 + 异名遗留键**：

  ```python
  if hasattr(config, "use_intraday_cache"):
      return bool(getattr(config, "use_intraday_cache"))
  return bool(getattr(config, "use_intraday_incremental_cache", False))  # 换了名字的旧键
  ```

  这种写法的真实兜底藏在**另一个名字**上，只扫 `getattr(config, X, 默认值)`
  是扫不出来的。verify.py 会把 `hasattr` 判定点单独标红要求人工看分支。

verify 报"缺第三方依赖"时，先判断是不是升级引入的：
官方常用元包收口依赖（`requirements.txt` 里只写一个包名），新版引入的三方库
是靠升级元包带进来的。所以"官方 requirements.txt 没变"不等于依赖没变。
优先升级元包（`uv lock --upgrade-package <元包>` 然后 `uv sync`），
不要单独 pin 一个版本去和官方依赖树打架。缺的库如果本来就没装（如 `lightgbm`），
还需确认它不影响当前运行；仅已确认的既有可选缺依赖可用 `--allow-missing-dependency lightgbm` 放行并报告，
不要顺手装。未放行的第三方依赖缺失会使验证失败，不能把失败默认降级成“全部通过”。

**装之前先确认框架实际用的是哪个解释器。** 仓库里有 `.venv` 不代表它就是运行时环境 ——
实盘类框架的启动配置（`startup.json` 之类）可能指向另一个 conda 环境。
装错地方等于没装，而且要到实盘启动失败时才发现。查一下启动脚本/配置里写的解释器路径。

全部通过后提交合并。提交信息里逐条写明各文件的冲突解决决定 ——
下次升级时这是唯一能还原"当时为什么这么合"的线索。

### 6. 汇报

说清楚：版本跨度、main 增删了什么、每个冲突文件怎么解决的、验证结果（含实际数字）、
依赖有什么变化、以及**需要人工复核的点**。

需要复核的点要老实列出来，包括 subagent 留下的 `TODO(merge ...)` 标注、
识别出的既有 bug、以及没能验证的部分。不要为了报告好看而省略。

**实盘类框架额外提醒一句交易模式。** 如果这是会真实下单的框架（仓管实盘、rocket 之类），
升级后检查一下当前是模拟还是实盘（`is_simulate` 这类开关），并在报告里点出来。
不要替用户改这个值 —— 那是真金白银的决定；但跨大版本升级后直接实盘跑，
风险值得明确提示一次，官方自己在公测版说明里也是这个态度。

## 收尾说明

不要顺手跑回测来"证明能用"。回测会覆盖已有结果目录，而官方跨大版本时
（例如换成 polars）计算结果本身就会有细微差异 —— 用户很可能正需要旧结果做对比。
要跑必须先问，并说明会覆盖什么。

旧版遗留的中间缓存（改过格式后失效的 pkl/parquet）可以提示用户清理回收空间，但不要自己删。
