# 合并简报模板

派发给冲突解决 subagent 的简报。把 `{{...}}` 换成实际值后写进临时文件，
让每个 subagent 先读它 —— 这样所有 subagent 共享同一套判断标准，不会各自发明规则。

简报值得单独成文而不是塞在 prompt 里，因为它是**跨 subagent 的共同宪法**：
四个 agent 各自只看三五个文件，但"官方骨架优先""本地路径不可覆盖""格式差异不算冲突"
这些原则必须完全一致，否则合出来的东西自相矛盾。

---

```markdown
# 合并任务背景 ({{仓库名}}: 官方 {{旧版本}} -> {{新版本}})

仓库: `{{仓库绝对路径}}`

当前处于 **merge 冲突未解决状态**（`git merge {{官方分支}}` 进行中，在 `{{本地分支}}` 上）。

## 两侧含义

| 冲突标记 | 含义 |
|---|---|
| `<<<<<<< HEAD` … | **ours = {{本地分支}}** = 用户自己的定制（本地数据路径、自定义因子/信号、格式化过的代码、新增功能） |
| … `>>>>>>> {{官方分支}}` | **theirs = 官方 {{新版本}}** = 官方新版框架代码 |

{{此处写官方本次的重点变更：从更新说明.md 摘要，说明是小版本迭代还是大规模重写。
如果跨了大版本（例如中间有一次 pandas->polars 重写），必须写清楚，因为这直接决定
subagent 该"以官方为骨架移植定制"还是"在 dev 基础上打补丁"。}}

## 解决冲突的原则（按优先级）

1. **官方的新架构/新 API 为基准**：凡是官方本次引入的新逻辑、新函数签名、新写法、
   新增配置项、新增指标 —— 必须保留。不要因为 dev 侧看起来"更完整"就整块丢弃官方代码。
2. **dev 的定制必须在新架构上重新落地**，不要静默丢掉。典型定制：
   - **本地真实路径**（数据目录、外部因子目录）—— 官方那侧是占位符
     （`/Users/xxxx/...`、`***参照注释填写***`）。**永远保留 dev 的真实路径**。
   - **API key / 实盘账户配置 / 资金与杠杆参数** —— 官方是样例值，一律保留 dev 的。
   - **策略选择与运行参数**（当前启用哪个策略、回测区间、并行数）—— 保留 dev 的。
   - 用户自定义的因子加载机制、评价指标、绘图、以及对 core 的扩展。

   ⚠️ **`config.py` 例外，别把本条读成"整块留 dev"**：正确解法是
   **业务值取 dev、公共配置键完整保留**。官方新增的公共配置键必须接入实际配置来源（用官方的默认值），
   动态profile配置应修改公共base/来源defaults而非破坏薄入口。明确互斥的选币/仓管字段保持当前模式，不能机械并集；
   只有"两边都有的键"才保留 dev 的值。整块留 dev 会让官方新键静默消失，
   而且不留任何冲突标记 —— 事后极难发现。真实事故：漏掉 `use_intraday_cache`，
   代码 fallback 把整条因子链路导回旧实现，撞上官方遗留缺陷直接崩。
3. **两侧都是"新增"时，合并保留双方**：
   - `import` 冲突 —— 保留双方全部 import（去重、按 stdlib/三方/本地分组）
   - 名单类配置（稳定币列表、黑名单）—— 对照基准区分增删，保留用户有意排除的条目；仅双方独立新增且语义兼容时取并集
   - 官方新增逻辑按新接口与调用顺序接入，不机械接在本地逻辑之后；尤其不能重复执行交易或资金变更
4. **纯格式差异不算冲突**：dev 侧常有整体重排版（black、单引号改双引号）。
   遇到"内容相同只是引号/换行不同"的冲突，保留 dev 的格式，
   但把官方的**实质内容变更**吸收进来。
5. **拿不准就报告具体分歧**：保留双方差异供主控审查，不要把两个行为硬拼进执行路径。
   `TODO(merge {{新版本}})` 只记录未决问题，不能作为安全或验证通过的依据；影响实际行为的分歧须在提交前解决。

## 取证命令（只读，安全）

```bash
git show :1:<file>              # 三方共同基准，不保证是纯官方旧版
git show :2:<file>              # ours   = 本地分支
git show :3:<file>              # theirs = 官方新版
git diff :1:<file> :3:<file>    # 官方这次到底改了什么
git diff :1:<file> :2:<file>    # dev 到底改了什么
git log --oneline -20 {{本地分支}} -- <file>   # dev 侧的改动意图（看 commit message）
```

先做三方对比，再结合提交历史判断"这段是官方新增还是 dev 新增"。
只看 `<<<<<<<` 两侧无法区分"对方删了"和"我加了"，务必用 `:1:` 做基准。
中文文件名在 bash 里要用双引号包裹。

## 严格禁止

- ❌ 不要运行任何改变 git 状态的命令：`git add`、`git commit`、`git merge`、
  `git checkout`、`git restore`、`git reset`、`git stash`、`git merge --abort`。
  主控统一负责暂存和提交 —— 多个 subagent 并发时，谁动索引都会破坏别人的工作。
- ❌ 不要碰不属于你任务范围的文件。
- ❌ 不要留下任何 `<<<<<<<` / `=======` / `>>>>>>>` 标记。

## 完成标准

1. 负责的文件中所有冲突标记已清除。
2. 语法通过：`python3 -c "import ast,sys;ast.parse(open(sys.argv[1],encoding='utf-8').read())" <file>`
3. 用 `git diff :2:<file> <file>` 自查：改动是否只有你预期的那几处？
   如果冒出意料之外的大段差异，说明误删了 dev 的定制。
4. **若你负责配置：必须做有效键级对账**。动态配置使用 `verify.py --effective-config`；只有明确选币/仓管互斥框架再加 `--config-layout selection-position`，禁止为凑齐字段而混用模式。下方 grep 仅用于平铺静态配置，不能作为动态配置的验收。确认官方公共键一个没丢
   （输出里带 `<` 的就是被你漏掉的官方键）：
   ```bash
   diff <(git show :3:config.py | grep -oE '^[a-zA-Z_][a-zA-Z0-9_]* *=' | tr -d ' =' | sort -u) \
        <(grep -oE '^[a-zA-Z_][a-zA-Z0-9_]* *=' config.py | tr -d ' =' | sort -u)
   ```
5. 报告：逐 hunk 说明决定、dev 定制逐条落地情况、需人工复核的点。
```
