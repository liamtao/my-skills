# 踩过的坑

按"什么时候会咬到你"排列。这些都是实战中真实发生过的，不是理论风险。

## git 与 shell

**中文路径被转义。** `git ls-tree` / `git status` / `git diff --name-only` 默认把非 ASCII
路径输出成 `"tools/tool1_\345\233\240\345\255\220..."`。用这种输出去做文件清单比对，
中文文件名会在两边都"只存在于一边"，产生一堆假的增删。
**所有** git 命令都加 `-c core.quotePath=false`。

**`&&` 链会被 grep/test 的退出码截断。** `grep -v ... && echo done` 里，
grep 没匹配到任何行时返回 1，后面整条链静默不执行。
实战中这导致过"以为 rsync 跑了，其实只删了旧文件没写新文件"——
而且因为没有报错，很容易误判成已完成。校验步骤用 `;` 分隔，或把校验放到独立命令里。

**`timeout` 在 macOS 上不存在**（那是 GNU coreutils）。别在命令里用。

**`git add -A` 在官方分支上是陷阱。** 官方分支的 `.gitignore` 往往极简（可能只有
`/data/ /logs/ /.idea/` 三行），不覆盖 `__pycache__`、`.DS_Store`、`.venv`。
而切到官方分支后，本地分支留下的 pyc 和虚拟环境仍在工作区里 —— `git add -A` 会把它们全提交进去。
正确做法：`git add -u`（只管已跟踪文件的改动与删除）+ 按官方文件清单显式 `git add <path>`。
`apply_official.py` 已经实现了这个配方，并在结束时自查暂存区有没有混入垃圾。

**切分支不会删掉只含忽略文件的目录。** 切到官方分支后，`configlib/`、`strategy/` 这些
本地分支独有的目录可能还在，因为里面残留着 `__pycache__`。它们不影响提交（已被显式暂存策略排除），
但会让 `ls` 的结果看起来很困惑。判断"工作区是否干净"要看 `git status --porcelain`，别看 `ls`。

## 版本与包定位

**下载目录名的版本分隔符不统一**：`select-coin-pro_v2.1.0`（下划线）、
`stock-fusion-v3.0.0`（连字符）。

**本地仓库目录名和官方包名可能不一致**：本地 `select_stock_pro` ↔ 官方 `select-stock-pro_v2.5.3`。
比对前要把分隔符归一化（`scout.py` 的 `norm()` 做了这件事）。

**同一框架常有多个历史版本包堆在下载目录**，且旧包的 mtime 可能因为解压顺序反而更新。
只按时间挑会挑错，要按版本号排序，并交叉验证包内 `core/version.py` 的 `sys_version`
与目录名上的版本是否一致。

**目录名的版本不一定等于包内版本。** 以包内 `core/version.py` 为准写提交信息。

## 分支与约定

**本地修改分支不一定叫 `dev`。** 见过 `dev-v3`（同时保留 `dev` 作为分叉备份），
也见过仓库当前就停在 `main` 上。别硬编码，优先取"当前所在分支"，
有多个候选时必须先问清楚 —— 合错分支的代价远大于多问一句。

**提交约定每个仓库不同**：`### v1.9.0`、`### v2.5.3 更新内容`、`v1.5.1`、
`官方框架升级 v2.5.3 → v3.0.0（…）`。照抄该仓库 `git log main` 的既有格式，不要自创。

## 官方包内容

**官方会停止分发某些目录。** 例如某版本随包发过 `private/` 工具脚本，下一版就不带了。
这时"全量替换"会把它从官方分支删掉，而如果本地分支从未改动过它，
合并时会连带从本地分支一起消失。备份 tag 可以恢复已跟踪文件；没有明确处理授权时询问，
已有选择就照做，例如 main 跟随官方删除、dev 恢复兼容插件。

**`.gitignore` 通常是你自己加的，官方包里没有。** 全量替换时必须显式保留，
否则会连同旧文件一起被删除，导致下一次 `git status` 里冒出成千上万个 pyc。

**被 gitignore 的目录里可能有必须更新的运行时文件。** 例如 `data/` 下的最小下单量表、
币种分类表。它们不进 git，所以 `git diff` 完全看不见，但直接影响能否跑起来
（有一次官方把 CSV 编码改成了带 BOM，同时新增了一个 json）。
这类文件要单独决策并先备份，因为它们可能是你手工维护过的。

**官方可能把更新说明的历史截断了。** 全量替换后 `更新说明.md` 可能只剩新版记录，
旧版本的变更历史被删掉（实测有一次少了 795 行）。这不算错误，但值得在报告里提一句 ——
旧内容随时可以从升级前的 tag 取回（`git show <tag>:更新说明.md`）。

**业务代码里有形似冲突标记的装饰分隔线。** 见过官方源码里写
`>>>>>>>>>>>>>>>>>> 2qgm <<<<<<<<<<<<<<<<<<<<<` 这种注释分隔线。
检测残留冲突标记时必须卡"恰好 7 个符号 + 空格或行尾"这个边界，
否则会误报 —— 而假警报比漏报更伤，它会让你不再信任这项检查。

**官方示例目录里的占位符是正常的。** `examples/`、`tools_official/`、`configlib/官方策略/`
里本来就写满 `/Users/xxxx`。占位符回归检查只扫"本次合并真正改动过的文件"，
否则会报出十几处无害告警，让你对告警脱敏，反而漏掉 `config.py` 里真正的回归。

## 依赖

**官方常用一个元包收口依赖**（例如 `requirements.txt` 里只写 `xbx-py11`）。
新版框架引入的新三方库（polars 之类）是靠升级这个元包带进来的，
所以"官方 requirements.txt 没变"不等于"依赖没变"。
升级后如果 import 失败提示缺某个库，先查元包的新版本是否已包含它，
优先走升级元包这条路，而不是单独 pin 一个版本 —— 后者会和官方的依赖树打架。

**区分"缺可选依赖"和"框架真坏了"。** 机器学习相关模块常缺 `lightgbm` 这类
本来就没装的可选依赖，这是既有状况，不是升级引入的回归。
顶层模块名只能区分“第三方”与“本仓库”，不能证明依赖可选或升级前就缺失。
未放行的缺依赖默认验证失败；只有升级前已确认且不影响当前运行的可选依赖，
才用 `verify.py --allow-missing-dependency <顶层包名>` 放行并在报告中列出。

## 合并本身

**大版本跨越时，diff 行数会骗人。** dev 侧改动 300 行、官方改动 40 行，
不代表该以 dev 为主 —— 官方那 40 行可能是新架构的接入点，丢了就整条链路断。
反过来官方重写了 1000 行时，硬保留 dev 的旧实现会让新特性全部失效。
要看的是**语义**：官方这次改的是骨架还是叶子。

**dev 修过的 bug 可能被官方新代码打回去。** 例如 dev 修了图表错位（给 4 个子图设了 domain），
官方新增了第 5 个子图 —— 修复本身还在，但没覆盖新子图，等于回归了。
凡是 dev 有过 bugfix 的地方，要检查官方新增内容是否需要同步扩展这个修复。

**pandas 定制不能直接粘进 polars 管道。** 跨重写版本时，dev 的定制往往是旧写法，
需要改写成与上下文一致的新写法，而不是原样插入。改写不确定就标 TODO 并报告，别硬猜。

**并发 subagent 不能碰 git 索引。** 多个 agent 同时解冲突时，
任何一个执行 `git add` / `git checkout` / `git merge --abort` 都会破坏其他 agent 的工作。
简报里要明确禁止，主控统一暂存提交。
