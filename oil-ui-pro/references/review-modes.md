# 评审手册：横向对比、任务走查、方案评审与复核

评审者专用，是 [评审手册](reviewer-manual.md) 的补充。主 Agent 派发时会写明按哪一节执行。已指定领域标准时，以下引用评审手册的检查项与评分锚点服从该领域覆盖；复核不更换上一轮使用的标准。

## 1. 多方向横向对比（查重）

同时看所有方向的截图（首屏或整页），只回答一个问题：哪些区块在不同方向里本质上是同一个东西（骨架和版式相同，只是换了颜色和字体）？逐个点名，要求退回按各自的方向重做。

## 2. 任务走查（纯交互与 UX）

先按 [轻量 UX 走查](ux-reviewer.md) 完成产品理解、主要路径和基础报告，再按本节深化。主 Agent 会指定【开放探索】或【复核】，共同的材料边界与诚信标准照那份文件执行。

### 开放探索

1. 到达主要结果后，再从当前页面可见的能力里自主选择一个与这条任务直接相关、你认为最可能让人困惑、误操作或丢失已有结果的风险点真实检查。你决定检查什么、怎样检查，不把功能清单逐项打勾；没有可安全探索的分支时写明依据，不为凑覆盖注入危险操作。区分页面声称成功和实际观察到的结果，能核对实际结果时不要只记录按钮变化。谎报成功、刷新丢已确认保存的数据是严重问题。游戏类另按 [游玩验收](play-craft.md) 的“交付和评审时多查几项”。
2. 在轻量报告的基础上，继续记录跨屏记忆、重复决定、不必要的页面切换和丢失的上下文。连续输入是否被焦点跳动、布局突变、滚动或动效打断；返回后对象、位置和输入是否还在。没有观察到的问题不写“流畅”，只写走了哪条路径、哪里没有遇到障碍。
3. 按任务影响排序补充关键问题，每条仍分开写观察事实、原因推断和建议达到的结果，并附对应截图或状态证据。

### 复核

1. 按上一轮报告复走同一路径，逐项判断**修好**、**修了一部分**或**没修**，每项给本次实际看到的证据；主 Agent 说修好了不算证据。
2. 检查上一轮路径是否仍然连贯，以及修改是否直接造成新的卡住、走错、犹豫或状态丢失。只报这批修改直接引入的问题，最多 3 条；不换角色、不另开新任务重新挑一遍。
3. 需要的状态在当前页面无法取得时写“无法核对”，不把未验证当通过。复核输出改写逐项核对结果，不重复整份开放探索报告。

## 3. 改流程与加新功能方案评审

比较多个交互方案：
1. 指出是否存在入口和步数都相同、纯粹是换了画面的假差异方案。
2. 指出哪一步还在让用户伺候界面（找入口、重复填已知值、为了确认而确认）。
3. 找出表面上的“补丁”设计（加了提示但没减少用户麻烦）。
4. **输出要求**：指出每个方案最可能失败的场景。不打分。

## 4. 复核（打分循环的第二轮起）

主 Agent 交来当前画面证据和上一轮的问题与提升清单；动效可用序列图或直接操作页面，录屏条件和判断边界按 [评审手册](reviewer-manual.md) 的“动效检查”。你的任务是核对，不是从头再评一遍：

1. 逐条判断上一轮的问题和提升：**修好**、**修了一部分**或**没修**，提升按做到位、做了一部分或没做来写，每条写一句当前截图、序列图或实际操作里看到的证据。主 Agent 说修好了不算数；证据不足以判断的记为“无法核对”。只是挪了位置、改了数值，问题本身还在的，算修了一部分。
2. 对照上一轮的“保留”一行，看那一处有没有被这批修改磨掉。磨掉了算新问题。
3. 这批修改带来的新问题最多写 3 条，按 [评审手册](reviewer-manual.md) 第 1 节的标准判断。上一轮没提过的老问题不在这一轮补，之后要不要另派全新评审由主 Agent 决定。新问题和“离下一档还差什么”里不写“再加一样”；只是对象变少、主角没有变大变强的减法，算修了一部分。
4. 截图明显不是当前版本时，只写这一点，不打分。核对某条问题需要的画面没给（例如某个状态），那条记为“无法核对”，不因此停评。
5. **输出要求**：逐条核对结果，新问题，最后按评审手册第 1 节的分数锚点重新打分。还有没修好的问题时，分数按这些问题的严重程度落档，不因为整体看起来好了一些就放过。
