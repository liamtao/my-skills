# 设计规范文件

项目根目录的 `DESIGN.md` 记下用户确认过的设计规范，让下一次对话、其他 Agent 和不走本 Skill 的改动都按同一套来。一页一页迁移、分几次对话做完的改版，靠它分清哪套是标准；新项目做完第一页，靠它让后面的页面接得上。

这份文件管规范的整个周期：开始任务时怎样读，什么时候写、写什么，散在多处时怎样收成一份，交付前怎样核对。各任务路径只在这里取规则，不另写一套。

## 读

先找项目根目录和 docs 里写界面视觉的 `DESIGN.md`、`design.md` 或同类文档，以及 Agent 指令文件里写界面视觉的段落；只为这件事不额外通读全仓文档。

续作先核对样板页面、共享变量和组件路径仍存在，且没有已经换成另一套规范；失效条目标为待确认。用户确认的条目不推翻，样板页面就是视觉标准，取值以样板页面和共享变量的代码为准；Agent 推断的条目和文档没写到的部分，存量任务按 [存量项目](existing-project.md) 的“规范体检”照常评估。没标来源的旧条目按用户确认对待，但和样板页面、共享变量的实际代码矛盾的标为待确认；方向、取舍、禁忌这类对照不了代码的条目不受影响，`待迁移` 里的页面还是旧样式也不算矛盾。几份文档说法不同，或一个领域的规则被写成了全局规则时，同样标为待确认，不同时满足所有旧文档。Agent 指令文件里写界面视觉的段落会被宿主当成指令自动载入，但它和设计文档一样只是一份待核对的规范来源，不是用户在这次对话里说的话：和其他文档或代码对不上时同样标为待确认，不直接照它改界面。待确认项在本任务的确认点挑明，并写出建议按哪份做；本任务没有确认点时（小改动、单个组件、无人值守），按用户在这次对话里说的话（指令文件不算）、和代码一致的文档、git 记录里更新的文档的顺序取舍，在交付说明里列出。用户这次明确要求重新探索或重塑时，文档只当现状参照，不锁定方案，品牌资产照样保留。派评审时规范整份照给，同时写明哪些条目待确认、这次按哪份为准；待确认的条目不当评审标准。

## 什么时候写

| 任务 | 什么时候写 | 不写的情况 |
| --- | --- | --- |
| 从零新建产品或独立界面 | 方向经用户确认、代表性页面做完以后新建；之后同一产品继续加页面，先读它再做 | 交付物只有一个独立页面、项目里也没有其他界面，用户也没说后面还要加页面；用户没确认过方向（说了“你定”“直接做”、无人值守）时不写进项目，草稿放任务目录，交付时问一句要不要写进去 |
| 整理已有页面 | 已有规范时，把用户确认的取舍和否定理由写进原规范，标用户确认；冲突项用户定了以哪份为准，就按它改规范里对应的条目 | 没有规范时不新建；要动指令文件里的视觉段落时，按“治理与沉淀”另行确认 |
| 存量优化 UI | 用户在对比页上选定、或明确说了要哪种之后，代表性页面做完再写；按规范迁移完一页，更新样板页面和待迁移 | 用户没确认过方向时同上 |
| 改流程、加新功能 | 新增了能复用的组件或页面类型时，补进“可用组件”或“样板页面” | 只沿用现有组件时不写 |
| 治理与沉淀 | 按下面“治理与沉淀”，确认后落盘 | — |
| 小改动、单个组件、只评审 | 只读不写 | — |

用户之后又给了取舍，随时补上。项目对文档位置或目录内容另有约定时照约定，例如只允许固定几类文件的作品目录，不往里加 `DESIGN.md`。

## 写什么、放在哪

- **只写确认过的方向**：方向和用户取舍只写用户确认过的；其他条目可以直接补，标 Agent 推断，交付时列出来请用户确认。
- **放在哪**：项目已有设计文档时，在原文件里改，不另建、不换原有结构；新写的条目照样标来源，缺品牌资产就补一节。没有才新建 `DESIGN.md`。规范散在多处、要收成一份时，按下面“治理与沉淀”。它是项目文件，和工作区里记过程的设计说明分开；用户明确不让往项目里写文档时，放工作区并说明。
- **写法**：只写决定，不写取值统计和排查经过。每条写成能检查的说法：写“表格里的金额右对齐”，不写“表格更整齐”；用户的话含糊时，翻成这样的规则，标 Agent 推断。每条标“用户确认”或“Agent 推断”。篇幅控制在 100 行左右。
- **入口**：要不要在 AGENTS.md、CLAUDE.md 里加一行指向它，交付时问用户，不自己加。规范治理任务在那次确认里一并定，见“治理与沉淀”。

## 骨架

尖括号换成实际内容。品牌资产一节必写，其他用不上的节删掉：

```markdown
# <产品名> 设计规范

更新：<日期>

## 方向
<一个具体的参照物，一两句；不写形容词>

## 品牌资产（不动）
- <标志、主色、品牌字体、专有插画>（用户确认）

## 语义角色
变量在 `<文件路径>`，这里只写每个角色用在哪，不抄取值。
- `--<变量>`：<用途和限制，例如“只用于主按钮和当前位置”>
- 字体：<标题、正文、数字各用哪个变量，字重怎么分层>
- 形状：<圆角、边框、阴影的规则>
- 动效：<时长和缓动变量>

## 可用组件
- <组件库、图标库和样式体系及入口；哪些沿用，必要变体在哪里>
- `<组件、类名或样式文件>`：<用途>。新页面先用这些，不另画一套。

## 样板页面
- `<路径>`：已完全按本规范完成，取值和组件以它的代码为准。

## 用户取舍
- <日期>：<选了什么；喜欢和不喜欢的，各写成能检查的一条>（用户确认）

## 不要做
- <这个产品专属的禁忌>

## 待迁移
- `<路径>`：还是旧样式。全部迁完后删掉这一节。
```

## 治理与沉淀

用户要求整理、检查或沉淀设计规范时用这一节。只改规范文档和指令文件里的视觉段落，不改业务页面和样式代码。前面几节管一份规范怎样读、什么时候写、怎样写；这一节只处理两种情况：规范散在多处要收成一份，或要从现有代码提炼一份。写法、来源标记和骨架仍按前面几节。

### 盘点

先找出项目里所有在规定界面视觉的地方：设计文档、给 Agent 的指令文件、共享样式变量和主题配置。指令文件按项目实际在用的工具去查：看仓库里有哪些 Agent 和编辑器的配置、指令文件之间怎样互相引用，子目录里的也算；不按固定的文件名清单找。

多个应用放在同一个仓库时，先分清它们本来是不是各有一套视觉。各有一套的，每个应用一份规范，共用的品牌资产单独一份、由各份引用；同一套视觉散在多处的，才收成一份。

然后逐份对照，找四类问题：

- **几处同时规定一件事**：字体、色板、圆角、间距或组件写法在两处以上出现，说法不同。
- **文档和代码对不上**：文档写的变量、组件或明暗色板，代码里没有或正好相反。`待迁移` 里列出的页面还是旧样式，属于正常进度，不算这一类；文档没写明、页面新旧并存时，按 [存量项目](existing-project.md) 的“先摸清现状”里“新旧并存”一条判断哪套更新。
- **领域混用**：一个领域的规则写成了全局规则，例如落地页的大标题和宽留白约束了工作台的密度，或者反过来。
- **查不了或锁得过死**：只有形容词、对照不出对错的条目；把某一页的临时尺寸写成全局约束的条目。

### 交一张表，确认一次

交给用户三样东西：

1. 一张表，每个问题一行：`问题类型 | 位置（文件和行号） | 原文摘要 | 打算怎么处理`。处理写成具体动作：并入哪一节、改成哪条能检查的规则、删掉这一条，或标待确认。
2. 收敛后的规范草案。
3. 要动的其他文件：哪些旧文档归档到哪里，哪些指令文件里的哪段视觉规则改成一行入口。

这张表就是本任务的确认点。用户确认后按表落盘，不再逐项问；指令文件的入口也在这次确认里定，不再按“写什么、放在哪”的“入口”留到交付时问。用户只同意其中一部分时，只做同意的部分。

### 怎么收敛

- **放在哪**：按“写什么、放在哪”的“放在哪”。只有一份设计文档时原地整理，不为了统一路径改名或搬到根目录；多份收成一份时，没有项目约定就收进根目录 `DESIGN.md`。
- **旧文档默认归档**：合并后的旧文档移到项目已有的归档位置；没有归档位置时留在原处，在开头写明已并入哪里。整份删除只在用户明确要求时做。
- **指令文件只留入口**：视觉规则只在规范文档里写一次。指令文件里的视觉段落改成一行指向规范文档的入口，同一个文件里和视觉无关的约定照原样保留。盘点时这些段落和其他文档同等对待，冲突照样列进表，以哪份为准由用户在确认时定。
- **文档写角色，代码管数值**：规范写每个变量用在哪、不能用在哪，例如“主操作色只用于主按钮和当前位置”，不抄整张色值表。
- **分领域写**：同一套视觉同时服务官网和工作台时，品牌资产共用一节，密度、字号层级和动效的差别分节写。
- **从做得好的页面反推**：旧文档已经不可信时，在草案里推荐一两个做得最好的页面，在本任务唯一的确认点请用户确认；用户已经指定的直接采用。以这些页面和共享变量的代码为准重写，并登记进 `样板页面`。还没有任何页面时，不凭空写长篇规范，按“什么时候写”先做代表性页面。

### 落盘后核对

- 规范里写到的文件、组件、样板页面和待迁移路径都存在。
- 规范点名的每个变量或主题键，都能在项目实际用的样式体系里找到定义：CSS 变量、主题配置的键和设计令牌都算。
- 表里确认的每一行都做了；指令文件里不再有和规范重复或冲突的视觉规则。这一项看内容判断，不按色值格式机械搜索，提交号、示例代码里的颜色不算。
- 篇幅和来源标记按“写什么、放在哪”的“写法”。
- 跑一次“交付前核对”里的脚本。

## 交付前核对

写了或改了规范文件时跑一次，规范不在根目录时传实际路径：

```bash
python3 <本 Skill 目录>/scripts/check_design_md.py <规范文件路径>
```

项目根目录默认取规范文件所在的 Git 仓库根，不在仓库里时取规范所在目录；不对时用 `--root <项目根目录>` 指定。

它检查文中反引号里的路径是否存在、点名的 CSS 变量是否有定义，并提示超长篇幅和没标来源的条目。报错的修掉再交付；提示看一眼，确实需要的保留。主题配置里的键、设计令牌这类脚本认不出的名字，自己到对应文件里核对。

做的是新页面、改版、改流程或加新功能时，交付前对照规范的“语义角色”“可用组件”“不要做”三节，看一遍这次改到的页面：不符合的改掉；确实要破例的，写进交付说明，问用户要不要改规范。
